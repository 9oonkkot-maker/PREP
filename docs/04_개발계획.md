# 카페 판매·손익·재고 관리 개발 계획

작성일: 2026-10-12  
상태: 사용자 확인 후 저장한 개발 계획. 계획 확정이며 실제 개발·검사·배포 완료를 의미하지 않는다.

## 현재 진행 상태

갱신일: 2026-10-12. 사용자가 문제없이 확인한 EPIC만 완료로 표시한다. 자체 검사 통과는 사용자 확인을 대신하지 않는다.

| EPIC | Story | 구현·자체 검사 | 사용자 확인 | 완료 여부 |
| --- | --- | --- | --- | --- |
| 1. 판매 기록과 메뉴 수익성 | US01~US04 | 구현 및 자체 검사 통과 | 사용자 “다 맞아”로 전체 확인 | 완료 |
| 2. 매장 손익과 재료 잔량 확인 | US05~US09 | 구현·자동 검사·브라우저 검수 통과 | 별도 사용자 확인 대기 | 미완료 |
| 3. 실제 재고 관리와 데이터 복구 | US10~US14 | 구현·자동 검사·브라우저 검수 통과 | 별도 사용자 확인 대기 | 미완료 |

검사 근거와 사용자 확인 기록은 `docs/05_테스트결과.md`에 남긴다. 사용자의 후속 요청에 따라 EPIC 2를 구현·검수했고 통과 후 EPIC 3도 구현·검수했다. 사용자 확인 완료와 자체 검수 통과는 구분한다.

## 1. 전체 작업 순서와 나눈 이유

작업 순서는 **판매·메뉴 수익성 → 매장 손익·재료 잔량 → 재고 기록·백업·복원**이다.

**총 3개 EPIC, 14개 User Story**로 구성한다. EPIC은 함께 완성할 작업 묶음, Story는 사용자가 한 가지 목적을 달성하는 기능 단위다. EPIC별 Story 수는 4개·5개·5개다.

판매 기록이 계산의 출발점이므로 먼저 만들고, 그 기록을 사용하는 손익·재고 조회를 연결한 뒤 실제 재고 관리와 복구를 완성한다. 각 EPIC이 끝나면 실제 화면에서 동작을 확인할 수 있어야 한다.

근거 문서는 `docs/01_PRD.md`, `docs/02_FRD.md`, `docs/03_TRD.md`이며 화면은 `design/_1`~`design/_5`의 시안을 따른다. 문서의 기능·사용 순서·계산 기준을 유지하고 시안에만 있는 추가 기능은 넣지 않는다. 2차 기능은 이번 개발 계획에 포함하지 않는다.

모든 Story는 **실제 자료 처리·저장·계산·기본 오류 처리·검증까지** 포함한다. 저장 실패 시 기존 자료 보존, 새로고침 후 기록 유지, 빈칸과 0 구분을 처음부터 검사한다. 화면만 만들거나 가짜 동작으로 완료 처리하지 않는다.

## 2. EPIC 1. 판매 기록과 메뉴 수익성

포함 Story: **US01~US04, 총 4개**.

선행 조건: 개발 환경을 준비하고 초기 자료·계산·검증·저장 기반을 구현한다. 이 기반은 US01의 실제 사용을 위한 작업이며 별도의 화면만 만드는 작업으로 완료 처리하지 않는다.

**완료 기준:** 제공 자료로 시작하여 판매를 등록·정정·삭제하고, 메뉴 수익성을 실제 계산 결과로 확인할 수 있다. 저장한 기록은 새로고침 후에도 유지되며 잘못된 입력·저장 실패에 대응한다.

| Story | 사용자가 할 수 있는 일 | 자동 검사 | 사용자가 화면에서 확인할 행동과 예상 결과 |
| --- | --- | --- | --- |
| **US01. 하루 판매 집계 등록** | 날짜·메뉴·채널·수량·단가·할인·수수료를 입력하고 저장한다. 기존 기록도 조회한다. | 초기 자료 한 번만 반영, 필수값·날짜·중복 검사, 순매출·원가 계산, 저장·재열기 검사 | 중복되지 않는 날짜에 10잔·4,800원·할인총액 3,000원을 입력한다. 순매출 **45,000원**이 표시되고 저장 후 새로고침해도 기록이 남는다. |
| **US02. 판매 기록 수정** | 잘못 입력한 판매 수량·가격·날짜·채널 등을 고친다. | 수정 전후 계산, 당시 기준 보존, 변경된 날짜·메뉴의 집계 갱신, 저장 실패 시 원본 유지 | 판매 수량을 바꾸면 순매출·총 원가가 바뀐다. 매장에서 포장으로 바꾸면 해당 포장 원가와 소모량이 반영된다. |
| **US03. 판매 기록 삭제** | 불필요한 기록을 한 건 또는 선택한 여러 건 삭제한다. | 삭제 취소, 선택 대상 검사, 일괄 삭제의 전체 성공·전체 취소, 관련 집계에서 제외 | 삭제 확인을 취소하면 기록이 남는다. 다시 삭제를 확정하면 목록에서 사라지고 관련 판매 합계가 줄어든다. |
| **US04. 메뉴 수익성 확인** | 일·월과 메뉴 분류를 선택해 판매량·원가·수수료·공헌이익을 확인한다. | 공헌이익·합계 이익률·반올림, 누락 원가·수수료, 순매출 0 처리 | 저장한 메뉴를 선택해 계산 근거를 본다. 공통 운영비는 메뉴에 배분되지 않는다. 수수료 미입력 기록은 **확인 필요**로 표시된다. |

공헌이익은 판매금액에서 재료·포장·결제수수료를 고려해 남는 금액이다. 임차료·인건비까지 고려한 매장 전체 손익과 구분한다.

초기 자료 반영·조회·저장은 US01의 실제 사용을 위한 기반으로 구현한다. 재고 소모 계산의 연결은 자동 검사로 확인하고, 재료 잔량 화면에서의 확인은 EPIC 2에서 수행한다.

## 3. EPIC 2. 매장 손익과 재료 잔량 확인

포함 Story: **US05~US09, 총 5개**.

선행 조건: EPIC 1의 판매 기록·계산·저장 기반을 사용한다. 비용 등록·수정·삭제를 준비한 뒤 매장 손익을 연결하고, 판매 소모와 기존 재고 기록을 사용하는 잔량 조회를 구현한다.

**완료 기준:** 판매·비용 변경이 일·월 손익에 연결되고, 판매에 사용된 재료를 반영한 잔량을 확인할 수 있다. 기존 자료의 입고·폐기·실측도 실제 계산에 포함한다.

| Story | 사용자가 할 수 있는 일 | 자동 검사 | 사용자가 화면에서 확인할 행동과 예상 결과 |
| --- | --- | --- | --- |
| **US05. 비용 기록 등록** | 실적에 포함할 날짜·기존 비용항목·금액·메모를 입력한다. | 날짜·금액·항목 검사, 월비용계획과 중복 합산 방지, 저장 검사 | 비용 5,000원을 등록한다. 해당 기간 비용이 5,000원 늘고 운영손익은 같은 금액만큼 줄어든다. |
| **US06. 비용 기록 수정** | 기존 비용의 금액·귀속일·항목을 고친다. | 같은 기록 ID 유지, 날짜 이동 시 이전·새 기간 갱신, 기존 배분 정보 보존 | 비용을 다른 날짜로 옮기면 이전 날짜에서 빠지고 새 날짜에 나타난다. 같은 비용이 두 번 남지 않는다. |
| **US07. 비용 기록 삭제** | 잘못 등록한 비용을 확인 후 삭제한다. | 취소 시 유지, 삭제 후 비용·손익 재계산, 저장 실패 시 원본 유지 | 삭제를 취소하면 변화가 없다. 확정하면 비용이 빠지고 손익이 그만큼 회복된다. |
| **US08. 일·월 실적과 손익 확인** | 매장 전체 매출·직접 비용·공통 비용·운영손익과 날짜별 내역을 본다. | 메뉴 결과와 매장 집계 일치, 휴무일 비용, 부분 기간·미마감·0분모 검사 | 판매와 비용을 수정한 뒤 같은 기간을 조회한다. 결과가 함께 바뀌며, 미마감 입력분은 **잠정**으로 구분되고 미래 날짜는 매출 0으로 채워지지 않는다. |
| **US09. 재료 잔량과 근거 확인** | 기준일·재료·공급사로 잔량을 조회하고 변동 이력을 본다. | 초기재고·판매 소모·입고·폐기·기존 실측 반영, 단위·기준일 검사 | 판매 수량을 늘리면 해당 재료 소모가 늘어난다. 최근 실측에는 날짜가 표시되고, 장부와의 차이는 같은 실측 시점을 기준으로 보인다. |

이 단계부터 **판매 입력 → 메뉴 수익성 → 매장 손익 → 재료 잔량**의 핵심 흐름을 끝까지 확인할 수 있다. 계산에 필요한 정보가 부족하면 결과를 확정값처럼 표시하지 않고 FRD의 확인 필요 기준을 적용한다.

## 4. EPIC 3. 실제 재고 관리와 데이터 복구

포함 Story: **US10~US14, 총 5개**.

선행 조건: EPIC 2의 잔량 계산·재고 조회와 기존 저장 기반을 사용한다. 재고 유형별 기록 관리를 구현한 뒤 전체 백업을 만들고, 그 백업으로 복원을 검사한다. US14는 US13의 유효한 백업 생성에 의존한다.

**완료 기준:** 입고·폐기·실측을 실제 기록으로 관리하고, 전체 백업으로 운영 기록과 기준정보를 복원할 수 있다. 취소·오류·복원 실패 시 기존 자료가 유지된다.

| Story | 사용자가 할 수 있는 일 | 자동 검사 | 사용자가 화면에서 확인할 행동과 예상 결과 |
| --- | --- | --- | --- |
| **US10. 재료 입고 기록 관리** | 들어온 재료를 등록하고 잘못된 입고 기록을 수정·삭제한다. | 묶음 수량 환산, 단위·구매금액 검사, 수정·삭제 후 잔량, 구매대금의 손익 중복 반영 방지 | 1,000ml 묶음 10개를 등록하면 **10,000ml**가 증가한다. 수량을 수정하거나 삭제하면 잔량도 바뀐다. |
| **US11. 재료 폐기 기록 관리** | 버린 수량을 등록하고 잘못된 폐기 기록을 수정·삭제한다. | 양수 입력을 음수 증감으로 처리, 단위 검사, 초과 폐기·음수 잔량 표시 | 100ml를 폐기하면 잔량이 100ml 줄어든다. 삭제하면 복구된다. 장부량보다 많이 폐기해도 임의로 0에 맞추지 않고 확인 필요를 알린다. |
| **US12. 마감 실측 재고 관리** | 실제로 센 수량을 기록하고 실측 오입력을 수정·삭제한다. | 실측 중복·음수 검사, 조정량 중복 차감 방지, 이후 실측 기준점 보존 | 장부 1,900ml일 때 실제 1,800ml를 기록하면 차이는 **-100ml**, 기준은 **1,800ml**다. 과거 판매를 고쳐도 실제로 센 수량 자체는 바뀌지 않는다. |
| **US13. 전체 데이터 백업** | 현재 저장된 운영 기록과 기준정보를 JSON 파일로 내려받는다. | 모든 필수 자료 포함, 같은 시점의 자료 읽기, 정밀도·빈값 보존, 생성 실패 시 원본 유지 | 백업을 내려받아 파일명·생성시각·기록 건수를 확인한다. 저장하지 않은 입력은 포함되지 않는다. |
| **US14. 전체 데이터 복원** | 백업 내용을 확인하고 현재 자료 전체를 교체한다. | 형식·버전·ID·참조·단위 검사, 복원 전후 일치, 취소·실패 시 전체 자료 보존 | 백업 후 기록을 바꾼 다음 복원한다. 백업 당시 판매·비용·재고와 계산 결과로 돌아간다. 잘못된 파일이나 취소에서는 현재 자료가 유지된다. |

입고·폐기·실측은 처리 기준이 달라 각각 나눴다. 각 Story의 수정·삭제는 **같은 종류의 재고 기록을 정확히 유지하기 위한 동작**이며 서로 다른 큰 기능을 묶은 것이 아니다.

## 5. 전체 진행과 최종 확인

1. **EPIC 1 완료:** 판매 입력·변경과 메뉴 수익성을 실제 화면에서 확인한다.
2. **EPIC 2 완료:** 비용·손익·재료 잔량까지 연결해 확인한다.
3. **EPIC 3 완료:** 재고 관리와 백업·복원을 확인한다.
4. **최종 검사·배포:** 전체 흐름, 저장 실패, 복원 오류를 검사한 뒤 GitHub에 코드를 보관하고 Vercel 운영 주소에서 다시 확인한다.

개별 Story에 포함한 자동 검사와 실제 화면 확인을 모두 통과해야 완료로 처리한다. 자동 검사는 사용자가 화면에서 수행하는 저장·다운로드·재열기·복원 확인을 대신하지 않는다. 실제 수행한 검사 결과와 남은 문제를 기록한다.

### 4시간 목표 계획

| 작업 | 시간 |
| --- | ---: |
| 기획 | 30분 |
| 화면 설계 | 20분 |
| 개발 | 125분 |
| 검사 | 40분 |
| 배포 | 15분 |
| 수정 여유 | 10분 |
| 합계 | 240분 |

기존 4시간 목표를 유지한다. 검사는 마지막에만 몰지 않고 각 EPIC에서 수행한다. GitHub·Vercel 접근 가능 여부는 착수 전에 확인한다. 필요한 외부 계정·배포 환경이 준비되어 있다는 전제의 목표이며 실제 완료 시간을 검증한 결과는 아니다.

시간 절약을 위해 2차 기능·별도 서버·로그인·기기 공유를 추가하지 않는다. 계산 정확성·데이터 저장·기본 오류 처리·검증은 생략하지 않는다. 시간 부족이나 환경 문제로 필수 기능을 완료하지 못하면 그 사실을 명시하며 화면이나 가짜 동작만으로 완료 처리하지 않는다.
