# 카페 판매·손익·재고 관리 기술 요구사항 문서(TRD)

작성일·공식 자료 확인일: 2026-10-12  
상태: 사용자의 추천안 위임에 따라 구현 방식을 정한 완료본. PRD·FRD의 기능·사용 순서·계산 기준을 변경하지 않는다. 문서 작성 완료이며 실제 코드·GitHub 저장소·배포·검사 완료를 의미하지 않는다.

TRD는 어떤 기술과 데이터 구조로 기능을 만들고 운영할지 설명하는 문서다. 기술 용어는 해당 항목에서 풀어 쓴다.

## 1. 구현 범위와 근거

근거: `docs/01_PRD.md`, `docs/02_FRD.md`, `design/_1`~`design/_5`의 이미지·HTML, `design/artisanal_operations/DESIGN.md`, 현재 `data/`의 설명·JSON 자료.

1차는 한 매장·운영자 한 명·한 대의 PC다. 초기 자료 반영, 판매·비용 직접 관리, 메뉴 수익성, 일·월 실적·손익, 재고 입고·폐기·실측·수정·삭제·잔량, 저장·전체 백업·복원을 구현한다. 엑셀 입력 양식·반복 가져오기, 나머지 기간, 예측·발주 추천, 기준정보 편집, 변경 이력·기기 공유는 2차다.

화면은 시안의 다섯 영역을 따른다. FRD에서 제외한 마감 승인·POS 연동·알림·리포트·실적 엑셀 내보내기·암호화 등을 구현하지 않는다. 시안의 숫자·메뉴·공급사·사업자번호·연락처는 원자료로 대체하거나 제거한다.

## 2. 권장 구성과 선택 이유

**Vercel은 화면과 프로그램 파일을 제공하고, 실제 운영 기록과 계산은 사용자의 PC 브라우저에서 처리한다. GitHub는 코드 보관 장소이고, 매장 기록의 저장·백업 장소가 아니다.**

| 기술 | 쉬운 설명 | 선택과 용도 |
| --- | --- | --- |
| React + TypeScript | 화면을 재사용 가능한 조각으로 만들고 입력·자료 형태를 개발 중 검사 | 다섯 화면·입력창·조회 상태 구현. React의 구성요소 방식 사용. [React 공식 안내](https://react.dev/learn) |
| Vite | 개발한 화면을 배포용 파일로 묶는 도구 | React·TypeScript 프로젝트, 정적 배포. 기본 출력 폴더 `dist`. [Vite 배포 안내](https://vite.dev/guide/static-deploy.html) |
| IndexedDB + Dexie | 브라우저 안에 많은 기록을 표로 보관하고 안전하게 읽고 쓰는 도구 | 운영 자료의 실제 저장소. Dexie로 조회·여러 표를 한 번에 저장하는 작업 관리. 별도 Dexie Cloud 서비스는 사용하지 않음. [Dexie 공식 문서](https://dexie.org/docs) |
| decimal.js | 소수 원가 계산에서 일반 숫자 계산의 미세 오차를 줄이는 도구 | FRD C01~C09의 금액·수량·반올림 구현. [decimal.js 공식 문서](https://mikemcl.github.io/decimal.js/) |
| Zod | 입력과 백업 파일이 정해진 자료 형태인지 검사하는 도구 | 초기 자료·입력·복원 검사를 통일. TypeScript 엄격 검사 사용. [Zod 공식 문서](https://zod.dev/) |
| CSS·SVG | 스타일과 간단한 그래프를 브라우저에서 그리는 표준 방식 | 시안 색상·표·입력창·날짜별 그래프 구현. 외부 차트·아이콘 CDN에 의존하지 않음 |
| Vitest | 작은 계산과 처리 규칙을 자동 검사하는 도구 | 계산·검증·오류 검사. 저장 검사는 테스트용 IndexedDB 환경과 실제 브라우저를 함께 사용. [Vitest 공식 안내](https://vitest.dev/guide/) |
| GitHub 비공개 저장소 | 코드의 변경 이력을 보관하는 장소 | 소스·문서·잠금파일·가상 샘플·검사 자료 보관. 실제 운영 백업 제외. [GitHub 저장소 안내](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories) |
| Vercel 정적 호스팅 | 인터넷 주소로 화면을 제공하는 서비스 | GitHub 연결로 검사 배포·운영 배포. 프로그램용 별도 서버·클라우드 데이터베이스·유료 데이터 동기화 없음 |

서버 없이도 한 기기에서 필요한 작업을 처리할 수 있어 4시간 범위를 줄일 수 있다. 로그인·다중 사용자 권한·서버 API를 1차에 추가하지 않는다. 공개 주소를 아는 다른 사람이 화면을 열어도 **그 사람 브라우저의 별도 자료**를 사용하며 운영자의 브라우저 기록을 조회하지 않는다. 같은 PC·브라우저 프로필에 접근하는 사람까지 차단하는 구조는 아니다.

Node.js는 로컬 개발·Vercel 빌드 모두 **24.x**로 맞춘다. Vite의 현재 요구와 Vercel의 지원 버전을 공식 문서로 확인했다. 프로그램 실행에 매장 PC의 Node.js 설치는 필요 없다. 패키지는 구현 시 호환되는 안정판을 설치하고 `package-lock.json`에 실제 버전을 고정한다. 문서에서 확인하지 않은 최신 세부 버전 번호를 추측하지 않는다. [Vite 요구 버전](https://vite.dev/guide/), [Vercel 지원 버전](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions).

## 3. 실행 구조와 기능 연결

```text
GitHub: 코드·문서·가상 샘플
  → Vercel 빌드·배포
  → HTTPS로 화면·프로그램·가상 초기 자료 제공
  → 사용자의 PC 브라우저
       입력/조회 화면
         → 입력 검사·계산 서비스
         → IndexedDB 저장
         → 저장 성공 후 집계·화면 갱신
       전체 백업 → 사용자 PC에 JSON 다운로드
       복원 파일 → 브라우저 내 검사 → 전체 자료 교체
```

브라우저에서 계산·복원을 할 때 실제 판매·비용·재고를 외부로 전송하지 않는다. 온라인 연결은 최초 화면·프로그램 파일을 받는 데 필요하다. 이미 열린 화면은 자료 조회·저장·백업을 브라우저 내부에서 처리한다. **오프라인에서 새로 열기·새로고침까지 보장하는 별도 설치형 기능은 1차에 넣지 않는다.**

| FRD 기능 | 화면·구현 담당 | 데이터 처리 |
| --- | --- | --- |
| F01 | 앱 시작·초기 반영 서비스 | 초기 JSON 검사 후 전체 표에 한 번 저장 |
| F02~F03 | 판매 화면·판매 입력창 | 날짜·메뉴·채널 조회, 거래 검사·저장, C01~C03·C07 연결 |
| F04 | 비용 화면·비용 입력창 | 귀속일·항목 조회, 비용 기록 저장·수정·삭제 |
| F05 | 메뉴 화면·읽기 전용 원가 설명 | C01~C04, 분류·채널별 수량·원가·상태 |
| F06 | 손익 화면·기간/일별 목록 | C05·C09, 확정·잠정·불완전 상태 |
| F07~F08 | 재고 화면·유형별 입력창·이력 | C06~C08, 실측 기준점 보존·잔량 재검토 |
| F09 | 공통 저장 서비스·저장 상태 | 원본 자료 쓰기, 실패 보존, 재열기 확인 |
| F10~F11 | 비용 화면의 백업·복원 영역 | 모든 표의 일관된 읽기·파일 생성·전체 교체 |

상단 다섯 메뉴는 주소의 `#dashboard`, `#sales`, `#menus`, `#inventory`, `#data`로 이동한다. 한 페이지 안에서 영역을 바꾸는 방식으로 새로고침 경로 오류를 줄인다. 이 주소는 자료 저장 위치나 조회 기간을 바꾸지 않는다. 백업/복원 버튼은 데이터 영역의 해당 부분을 연다.

화면 표시 상태는 React의 공통 상태 관리로 전달하되 **저장 원본은 IndexedDB 하나**다. 표와 그래프마다 따로 금액을 계산하거나 예시 숫자를 남기지 않는다. 필터·선택 행·입력창 임시값은 화면 상태이며 원본 거래가 아니다.

## 4. 데이터 구조와 저장

### 표와 주요 조회 키

키는 기록을 빠르게 찾는 기준이다. 표에 있는 ID는 대상의 고유 번호이며 이름 변경·표 정렬로 바뀌지 않는다.

| 표 | 주요 자료 | ID·조회 기준 |
| --- | --- | --- |
| suppliers | 공급사 이름·자료 구분 | supplier_id |
| materials | 단위·구매용량·최초가격·납기·여유 일수·공급사 | material_id, supplier_id |
| menus | 메뉴명·가격·분류·현재 레시피 버전 | menu_id, category |
| recipes | 버전·메뉴·재료·사용량·적용채널 | 버전+메뉴+재료+적용채널의 복합 키 |
| price_history | 재료·적용일·구매가격·용량 | 재료+적용시작일의 복합 키 |
| calendar | 영업·마감 여부·날씨·메모 | date |
| opening_inventory | 초기 날짜·재료·수량·단위 | 재료+기준일 |
| sales | 원자료 판매 항목, 당시 원가·레시피, 수정 확인 번호 | sale_id, date, menu_id, 날짜+메뉴+채널의 유일 키 |
| expenses | 귀속일·항목·금액·기존 배분 설명·선택 메모 | expense_id, date, category |
| inventory_events | 유형·날짜·재료·증감·실측·단위·입고원가·사유 | event_id, 날짜, 재료+날짜 |
| monthly_expense_plan | 월·항목·계획 금액 | 월+비용항목 |
| dataset_meta | 자료 출처·기간·통화·샘플 구분 | 단일 자료정보 |
| app_meta | 초기 반영 완료·저장시각·자료 변경 번호·형식 버전·운영 기준 | 단일 앱 상태 |

자료 변경 번호는 저장 작업마다 증가하는 번호다. 같은 행을 다른 탭에서 바꾼 뒤 오래된 입력창으로 덮는 일을 막는 데 사용한다. 전체 매장 운영 기록은 단일 매장 자료로 관리하며 여러 매장을 위한 구조를 1차에 추가하지 않는다.

### 값의 표현

- 날짜는 `YYYY-MM-DD`, 월은 `YYYY-MM`로 저장한다. 영업 날짜를 UTC 시각으로 바꾸어 하루가 바뀌지 않도록 한다. 저장·백업 시각은 UTC 시각으로 보관하고 한국 시각으로 표시한다.
- 입력 금액과 개 수량은 정수 조건을 검사한다. 계산용 금액·g/ml·소수 원가는 십진수 문자열로 저장해 decimal.js에 전달한다. 화면에 보이는 천 단위 쉼표·원·단위는 저장 값에 넣지 않는다.
- 빈칸은 `null` 또는 항목 없음으로 보존한다. `0`·빈 문자열·미입력을 같은 값으로 바꾸지 않는다. 원자료의 수수료·당시 단가·원가·할인·순매출은 가져온 값의 의미·정밀도를 유지한다.
- 기존 ID는 유지하고 새 거래는 중복되지 않는 새 ID를 발급한다. 최초 샘플과 신규 거래를 같은 ID로 덮지 않는다.
- 가격 이력과 레시피는 1차에서 읽기 전용이다. 신규 입고 구매금액을 저장했다고 가격 이력을 자동 바꾸지 않는다.
- 원자료 I10(포장컵세트)·I11(디저트포장세트)을 포장 재료로 명시해 식재료비와 구분한다. 판별을 이름 문자열에 맡기지 않는다.

### 저장 절차

1. 입력 검사와 미리보기는 임시 상태에서 수행한다.
2. 저장 시 현재 자료 변경 번호와 입력창을 연 당시 번호를 비교한다. 바뀌었으면 기존 입력을 보존하고 다시 불러오도록 안내한다.
3. 하나의 읽기/쓰기 **트랜잭션**에서 대상 행·저장시각·변경 번호를 함께 반영한다. 트랜잭션은 작업 전체를 성공시키거나 전체를 취소하는 저장 단위다.
4. 성공 후 관련 집계 캐시를 무효화하고 다시 계산한다. 성공 전에는 완료 상태·새 화면 합계를 확정하지 않는다.
5. 다른 탭에는 변경 알림을 보내고, 탭이 다시 활성화될 때 변경 번호도 재확인한다. 알림은 클라우드 동기화가 아니다.

선택 삭제도 단일 트랜잭션에서 처리한다. 저장 실패를 내부에서 무시하여 일부만 반영하지 않는다. 초기 자료·전체 복원의 여러 표 저장은 같은 트랜잭션 안에서 처리하고, 실패 처리는 바깥에서 한다. Dexie는 대량 쓰기를 트랜잭션 밖에서 사용하면 일부 성공한 자료가 남을 수 있으므로 반드시 묶는다. [Dexie 트랜잭션 안내](https://dexie.org/docs/Dexie/Dexie.transaction()), [대량 쓰기 주의사항](https://dexie.org/docs/Table/Table.bulkPut()).

IndexedDB는 주소의 출처(프로토콜·호스트·포트)와 브라우저 프로필에 묶인다. 운영 URL을 하나로 고정한다. 검사 배포 URL·다른 도메인·시크릿 창·다른 브라우저에는 자동으로 같은 기록이 나타나지 않는다. 자료 보관을 지속하도록 브라우저에 요청할 수 있지만 승인과 공간은 브라우저가 결정하며, 사이트 데이터 삭제까지 막지 못한다. [브라우저 저장 정책](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

## 5. 초기 자료와 가져오기

가상 샘플 JSON만 배포 자산 `public/sample/prep-cafe.json`으로 준비한다. 실제 원자료의 필드와 금액을 시안에 맞춰 변경하지 않는다. 배포 전 샘플 여부와 불필요한 개인정보가 없는지 확인한다. 원본 엑셀·설명·시안 전체를 공개 자산에 복사하지 않는다.

첫 실행 시 저장소 열기에 성공하고 초기 반영 상태가 없으며 운영 표가 비어 있는 경우에만 JSON을 읽는다. Zod로 구조·자료형을 검사한 뒤 ID·참조 관계·단위·중복 조합을 별도 검사한다. JSON을 먼저 검사하고 저장 트랜잭션을 시작하며 트랜잭션 안에서 네트워크 요청을 기다리지 않는다.

모든 표 반영과 초기 완료 표시가 함께 성공해야 한다. 저장소를 열지 못한 경우를 ‘자료 없음’으로 처리하지 않는다. 완료 상태와 실제 표가 맞지 않으면 확인 필요로 중단하고 초기 자료를 다시 넣지 않는다. 운영 기록이 비어 있는 유효한 백업을 복원했을 때도 초기 완료 상태를 유지해 샘플 재반영을 막는다.

원자료에서 모르는 참조·단위·중복 ID 등 구조 오류는 초기 반영 중단, 미입력 원가·수수료·원본 계산 불일치는 원본 보존과 해당 결과의 확인 필요로 처리한다. 기존 기록을 새 입력 날짜 규칙으로 일괄 거부하지 않는다.

1차의 ‘가져오기’는 초기 JSON 반영과 프로그램 백업 복원뿐이다. 사용자가 임의 엑셀·원자료 JSON을 반복 가져오는 창은 만들지 않는다. E01 엑셀 기능은 2차에서 동일 검증 서비스와 계산 모듈을 재사용하며 라이브러리·열 양식은 그 단계에서 정한다.

## 6. 계산 구현과 결과 정확성

FRD C01~C09를 **화면과 분리된 계산 모듈** 한곳에 구현한다. 같은 입력은 어느 화면에서 계산해도 같은 결과를 내야 한다. 함수는 원본을 수정하지 않고 결과와 확인 필요 사유를 돌려준다.

| 모듈 | 구현 책임 |
| --- | --- |
| 판매 계산 | C01 순매출·C03 공헌이익·수수료 금액 보존·할인 범위 검사 |
| 원가 계산 | C02 판매일 이하 최근 가격·해당 레시피·채널 재료, 당시 저장값 보존 |
| 기간 집계 | C04·C05·C09, 메뉴·채널·비용별 합계, 확정/잠정/불완전 상태 |
| 재고 계산 | C06~C08, 초기재고·입고·폐기·조정·소모·실측, 기준일별 잔량 |
| 표시 처리 | 원·단위·천 단위 표기, 금액과 비율 반올림, 반올림 차이 안내 |

decimal.js 연산 정밀도는 40자리로 설정하고 중간 계산을 화면 정밀도로 자르지 않는다. 화면에서는 FRD대로 최종 금액 원 미만, 비율 소수 둘째 자리에서 반올림한다. `ROUND_HALF_UP` 방식으로 절반일 때 0에서 멀어지도록 처리한다. 결과 캐시·백업에 표시용 반올림 숫자를 원본으로 넣지 않는다. 0분모는 계산 불가 상태이며 `NaN`·무한대·0% 대체 금지.

계산 결과는 ‘값 있음’, ‘확인 필요’, ‘계산 불가’, ‘기록 없음’을 구분한다. 누락 수수료·원가가 있는 행을 제외한 합계를 전체 이익이라고 표시하지 않는다. 정상 매출 합계와 이익의 불완전성을 따로 반환한다. 비율은 합계 금액으로 계산하며 메뉴별 비율을 평균하지 않는다.

기존 판매의 당시 원가는 계산 입력으로 사용하고 현재 가격으로 바꾸지 않는다. 신규 기록은 C02 기준값을 저장한다. 단순 수량 수정은 개당원가를 유지하며 날짜·메뉴·채널 변경은 FRD에 따라 새 조건 원가를 미리보기하고 저장한다. 수수료는 금액이며 수량 수정 때 자동 2.5%로 다시 만들지 않는다.

재고는 재료·날짜 순서로 처리하고 당일 입고·소모·폐기/조정 후 마감 실측을 적용한다. 실측수량이 있는 행은 새 기준점이다. 그 행의 증감량은 비교 정보이며 다시 증감으로 더하지 않는다. 실측 없는 기존 조정은 증감량을 반영한다. 과거 판매 수정 후 실측 직전 장부·차이는 다시 계산하지만 이후 실측수량은 유지한다. 확인 불가능한 과거 실측의 시간은 실제 사실로 채우지 않는다.

입고원가는 정보로 저장하지만 구매대금을 손익에서 또 빼지 않는다. 1차 손익은 판매 재료·포장·수수료와 기간 공통 비용이며 폐기손실 금액 계산을 추가하지 않는다. 미래 영업일을 매출 0인 실적으로 만들지 않고 미마감 입력분은 잠정 상태로 분리한다.

## 7. 백업·복원과 버전 관리

### 백업 파일

백업 형식 1로 시작한다. 최상위는 프로그램을 구분하는 `format`, `backupVersion`, `appVersion`, `createdAt`, `datasetMeta`, `rulesVersion`, `counts`, `data`를 갖는다. `data`에는 4절의 운영 표·기준정보·원자료 메타와 복원에 필요한 운영 기준을 모두 넣는다. 날짜·원가 정밀도·미입력 상태·기존 ID를 보존한다. 화면 집계 캐시는 넣지 않는다.

읽기 트랜잭션에서 모든 표와 동일 자료 변경 번호를 읽어 서로 다른 시점의 판매·재고가 섞이지 않게 한다. 트랜잭션 종료 뒤 JSON을 만들고 브라우저의 다운로드 기능으로 `prep_backup_YYYYMMDD_HHmmss.json`을 제공한다. 파일을 읽거나 생성하는 작업은 PC 안에서 수행한다. 다운로드 시작 안내와 파일 보관 성공을 혼동하지 않는다. 백업 생성 실패는 원본을 변경하지 않는다.

저장소 버전, 백업 형식 버전, 프로그램 버전은 따로 관리한다. 프로그램 업데이트로 백업 읽기가 갑자기 바뀌지 않게 한다. 초기 JSON은 백업 식별자가 없으므로 F11의 복원 파일로 취급하지 않는다.

### 복원 절차

1. 파일을 메모리에서 읽고 JSON 구조·지원 버전·운영 기준 버전·표별 건수·ID·참조·단위를 검사한다. 외부 파일의 객체를 실행하지 않고 허용된 필드만 자료로 읽는다.
2. 필요한 모든 행을 정규화한 뒤 검증 결과·교체 요약을 보여준다. 알고리즘 정책을 알 수 없는 백업은 현재 정책으로 억지 변환하지 않는다.
3. 사용자 전체 교체 확인 후, 준비된 자료로 단일 쓰기 트랜잭션을 수행한다. 거래 표와 기준 표·메타를 함께 교체한다. 원본을 먼저 비운 뒤 별도 저장하지 않는다.
4. 현 저장소 변경 번호는 이전 값보다 증가시켜 다른 탭의 오래된 편집을 막는다. 초기 반영 완료를 유지하고 집계 캐시를 전부 폐기한다.
5. 성공 후 원본에서 모든 결과를 재계산한다. 오류는 전체 롤백하고 기존 자료를 유지한다. 전원 종료·창 닫힘의 트랜잭션 취소도 실제 브라우저에서 검사한다.

1차는 지원하는 백업 버전만 복원한다. 후속 버전은 명시적 변환기를 마련하고 이전 백업 검사에 통과해야 한다. 변경 이력·자동 백업·부분 병합 복원·백업 암호화는 추가하지 않는다. 브라우저 저장소 자체가 삭제되면 외부에 보관한 백업이 복구 수단이다.

## 8. 개인정보·운영 정보 보호

- 고객 이름·연락처·결제카드·개별 주문·직원 신상은 기능상 수집하지 않는다. 비용·재고 메모는 글자 자료로만 표시하고 HTML로 실행하지 않는다.
- 실제 운영 자료·복원 파일·메모를 GitHub·Vercel·외부 분석·오류 수집 서비스로 보내지 않는다. 개발자 콘솔에도 실제 거래 본문을 남기지 않는다. 오류는 유형·기능·시각과 필요한 비식별 상태로 제한한다.
- GitHub 저장소는 비공개로 권장한다. 비공개 저장소를 사용해도 배포된 정적 파일은 열람될 수 있으므로 실제 기록·백업·비밀키를 배포 파일에 넣지 않는다. `.gitignore`로 실제 백업, `.env`와 운영 자료를 제외하고 커밋 내용을 확인한다.
- Vite의 공개 환경 설정에 비밀키를 넣지 않는다. 1차에는 서버 API와 비밀키가 필요 없다. 향후 필요해지면 서버 쪽 처리와 범위를 별도 설계한다.
- 시안의 외부 Tailwind 실행 스크립트·Google Fonts·외부 사진을 그대로 연결하지 않는다. CSS는 빌드 파일에 포함하고 글꼴은 시스템 한글 글꼴을 사용한다. 아이콘은 배포에 포함한 SVG로 제공한다.
- Vercel은 HTTPS 주소를 사용한다. CSP(허용된 파일만 실행하도록 제한하는 보안 정책)는 스크립트·연결을 기본적으로 같은 사이트로 제한하고 외부 iframe 포함을 차단한다. `script-src 'self'`, `connect-src 'self'`, `object-src 'none'`, `frame-ancestors 'none'`, `base-uri 'self'`를 적용한다. 필요 스타일은 빌드 CSS를 기본으로 하되 React 스타일 속성 사용 여부에 맞춰 스타일 정책만 조정한다. [CSP 안내](https://developer.mozilla.org/en-US/docs/Web/Security/Practical_implementation_guides/CSP).
- 추가로 MIME 혼동 방지와 참조 주소 전송 최소화 헤더를 설정한다. JSON 백업은 평문이므로 공유 PC·공유 폴더에 두지 않도록 사용 안내에 명시한다. 비밀번호·앱 암호화가 있는 것처럼 표시하지 않는다.
- GitHub·Vercel 계정에는 계정 보호 설정을 권장하고 저장소 연결 권한을 해당 프로젝트로 제한한다. 이것은 앱 로그인 기능 추가가 아니다.

로컬 저장은 서버 유출 범위를 줄이지만 PC 사용자·브라우저 확장 프로그램·악성 스크립트로부터 절대 보호를 제공하지 않는다. Vercel 서비스 제공 과정의 접속 로그까지 사라진다는 뜻도 아니다. 실제 거래를 서비스로 보내지 않는 것과 사이트 접속 정보가 처리되는 것을 구분한다.

## 9. 처리 속도와 데이터 증가 대응

현재 JSON은 약 3.46MB이고 운영·기준 기록은 약 1만 2천 행이다. 아래는 측정 전 **검사 목표**이며 성능 보장이 아니다. Windows PC의 최신 안정 Chrome·Edge, 8GB 이상 메모리, 동일 샘플과 정상 저장 공간을 기준으로 측정한다.

| 작업 | 목표 | 구현 방법 |
| --- | --- | --- |
| 최초 자료 반영 | 자료 다운로드 이후 검사·저장·화면 준비 3초 안팎 | JSON 한 번 읽기, 대량 저장, 중복 반영 금지 |
| 일반 기간 조회·메뉴 집계 | 대표 조회 0.5초 이내 | 날짜 인덱스 조회·필요 자료만 집계, 같은 결과 재사용 |
| 저장 후 연결 결과 갱신 | 대표 작업 1초 이내 | 거래 한 번 저장, 해당 범위 캐시 무효화 |
| 재고 잔량 조회 | 샘플 기준 1초 이내 | 재료별 소모량·변동 묶음, 실측 기준점 이후 계산 |
| 전체 백업·복원 | 대표 작업 5초 안팎 | 일관된 일괄 읽기·검사·대량 쓰기, 진행 상태 표시 |

목록은 한 페이지 50행으로 표시하되 전체 조건의 합계는 전체 해당 기록에서 계산한다. 검색은 입력 후 짧게 기다려 연속 재계산을 줄인다. 소량 기준정보는 메모리에 보관하고 날짜별 판매·비용·재료 소모 집계는 자료 변경 번호와 조회 조건으로 캐시한다. 캐시는 저장·복원 실패 시 확정 결과로 갱신하지 않는다.

별도 작업 스레드·복잡한 가상 스크롤·영구 집계표는 1차에 선행 추가하지 않는다. 목표를 못 맞추면 실제 느린 구간을 측정해 같은 기능 안에서 최적화한다. 향후 자료가 늘면 대량 파일 처리·저장 공간·메모리 목표를 다시 정하며 클라우드 공유로 조용히 전환하지 않는다.

| GitHub | 필요한 비공개 저장소와 연결 권한만 사용. 기존 계정·실제 요금제 확인 |
| 도메인 | 기본 Vercel 운영 주소로 시작. 별도 도메인 구매는 하지 않음 |
| 외부 분석·폰트·백업 서비스 | 사용하지 않음. 운영자가 JSON 백업 파일 보관 |

정적 배포라도 다운로드·빌드·네트워크 사용료가 영구적으로 0인 것은 아니다. 초기 샘플을 매번 불러오지 않고 불필요한 재배포를 줄인다. Vercel 지출 알림을 설정하고 초과 사용 대응을 확인한다. 비용 제어로 배포가 중단될 경우 앱을 새로 받지 못할 수 있으므로 이미 보관한 백업이 중요하다. 문서에서 유료 가입·결제·배포를 실제 실행하지 않는다.

## 11. 오류 대응과 복구

| 오류 | 구현 동작·사용자 안내 |
| --- | --- |
| 입력·파일 구조 오류 | Zod 항목 위치와 업무 검증 사유를 쉬운 문구로 표시. 입력 보존, 저장 전 중단 |
| 저장소 열기 실패 | 초기 샘플 자동 재반영 금지. 재시도·같은 브라우저/주소 확인 안내 |
| 저장 공간 부족 | 트랜잭션 취소. 미저장 표시·입력 보존. 읽기 가능하면 백업 제공 |
| 저장 중 탭 충돌 | 변경 번호 불일치 시 덮어쓰기 중단. 기존 입력과 재불러오기 안내 |
| 원가·수수료·소모량 누락 | 해당 결과 확인 필요. 영향을 받지 않는 값만 독립적으로 표시 |
| 잔량 음수 | FRD대로 실제 기록 유지, 확인 필요 표시. 자동 0 보정 없음 |
| 복원 검사·쓰기 실패 | 전체 교체 중단/롤백. 기존 자료 유지, 파일·버전·저장 오류 구분 |
| 계산·화면 예외 | 잘못된 결과를 0으로 숨기지 않음. 입력 가능한 영역과 실패 영역 구분, 다시 조회 안내 |
| 프로그램 배포 오류 | 이전 정상 코드로 Vercel 배포 복귀. 운영 DB 삭제·샘플 재초기화 금지 |
| 브라우저 자료 삭제·PC 고장 | 운영자가 외부 보관 백업으로 전체 복원. GitHub 코드나 배포 복귀가 거래 복구를 대신하지 않음 |

저장소 구조 변경은 버전별 전환 코드를 사용하고, 삭제 후 다시 만드는 방식을 피한다. 데이터 전환이 들어가는 배포 전에는 현재 백업을 확보한다. 이전 코드가 새 자료 구조를 읽을 수 있는지 확인하지 않고 코드만 되돌리지 않는다. 이전 코드 복귀와 거래 데이터 복원은 별도 작업이다.

## 12. 코드 구성과 개발·배포 순서

| 위치 | 책임 |
| --- | --- |
| `src/pages/` | 손익·판매·메뉴·재고·데이터 다섯 화면 |
| `src/components/` | 입력창·표·기간 선택·상태·확인 조작 |
| `src/domain/` | 거래 검증·C01~C09·자료형·확인 필요 상태 |
| `src/storage/` | Dexie 표·초기 반영·트랜잭션·변경 번호 |
| `src/backup/` | 백업 형식·일관된 읽기·검증·복원 |
| `src/styles/` | 시안의 색상·숫자·입력·표 스타일 |
| `tests/` | 계산·검증·저장·복원 자동 검사 |
| `public/sample/` | 검토된 가상 초기 JSON만 배포 |
| `docs/` | PRD·FRD·TRD 및 후속 개발 계획 |

위 경로는 구현 예정 구조이며 이번 문서 작성으로 생성된 코드 경로가 아니다.

1. 로컬 프로젝트를 React·TypeScript·Vite로 준비하고 Node 24.x·잠금파일·엄격 타입 검사를 맞춘다.
2. 계산·검증·저장 기반부터 구현한다. 다음으로 판매→메뉴 수익성→비용·손익→재고→백업·복원을 연결한다. 초기부터 원본 저장과 오류 처리를 포함한다.
3. 시안 HTML의 실제 필요한 구조를 React 구성요소로 옮기고 고정 숫자·외부 스크립트·제외 조작을 제거한다.
4. 타입 검사·자동 검사·배포 빌드를 통과하고 실제 브라우저의 핵심 흐름·재열기·복원을 확인한다.
5. GitHub의 해당 비공개 저장소에 코드·문서·잠금파일을 보관한다. 사용자 지정 저장소가 있으면 그것을 사용한다. 실제 운영 기록은 커밋하지 않는다.
6. Vercel에 저장소를 연결한다. 프레임워크 Vite, 설치 `npm ci`, 빌드 `npm run build`, 출력 `dist`, Node 24.x를 사용한다. Hash 주소 이동이므로 1차는 개별 화면의 서버 경로를 추가하지 않는다. [Vercel Vite 안내](https://vercel.com/docs/frameworks/frontend/vite).
7. 검사 배포에서 가상 자료로 확인하고 운영 브랜치의 정상 결과를 운영 배포한다. 검사 URL과 운영 URL의 브라우저 저장소가 다름을 알린다. 최종 운영 주소와 기준 프로그램 버전을 기록한다.

정확한 GitHub 저장소·Vercel 프로젝트·계정·도메인은 아직 제공되지 않았다. 이는 구현 선택을 미정으로 남긴 것이 아니라 실제 배포 때 확인할 외부 자원이다. 임의의 저장소 이름·URL을 기존 자원으로 단정하지 않는다.

PRD의 총 240분 계획은 기획 30분·화면 설계 20분·개발 125분·검사 40분·배포 15분·수정 여유 10분을 유지한다. 시간 절약을 위해 서버·로그인·2차 기능을 추가하지 않고 표·입력·간단한 그래프 중심으로 구현한다. 핵심 계산·저장·검사를 시간 부족을 이유로 가짜 결과로 대체하지 않는다.

## 13. 검사와 배포 완료 기준

| 자동 검사 | 실제 화면 확인 |
| --- | --- |
| FRD 숫자 예시: 순매출 45,000·공헌이익 36,725·손익 16,725·이익률 81.61 | 같은 가정 기록을 입력해 미리보기와 실제 저장 결과 확인 |
| 날짜별 가격·채널 레시피·소수 원가·0분모·빈값 | 매장/포장 전환·미입력 수수료·순매출 0에 대한 안내 확인 |
| 거래 추가·수정·삭제·중복 검사·변경 번호 충돌 | 판매 변경이 메뉴·손익·재고에 연결되는지 확인 |
| 실측 기준점·폐기·과거 판매 수정 | 실측 1,800ml가 유지되고 장부 차이만 달라지는지 확인 |
| 비용 귀속·휴무일·월계획 중복 방지·부분 기간 | 잠정/확정 상태와 미래 날짜를 0으로 채우지 않는지 확인 |
| 원자적 저장·일괄 삭제·초기 중복 반영 방지 | 새로고침·브라우저 재열기·저장 실패 후 기록 유지 확인 |
| 백업 전후 원본 일치·잘린 파일·알 수 없는 버전·저장 실패 | 다운로드 후 복원, 취소·오류·창 닫힘에서 기존 자료 유지 확인 |
| 타입 검사·일관된 빌드·지원 백업 호환 | 운영 주소·Hash 이동·보안 헤더·제외 버튼 정리 확인 |

자동 검사는 Vitest와 테스트용 IndexedDB를 사용하되 실제 브라우저 저장·다운로드·트랜잭션 종료 검사를 대신하지 않는다. 오류는 실패를 주입한 검사에서도 확인한다. 가상 자료로 개인정보 전송이 없는지 네트워크 요청을 확인한다.

완료 조건은 필수 기능의 실제 동작, 동일 기준 계산, 새로고침 후 저장 유지, 유효한 전체 백업·복원, 오류 시 기존 자료 보존, 원자료·시안 범위 정합성, 검사 통과, 확인된 GitHub 커밋과 Vercel 운영 URL이다. 현재는 TRD만 완료했으며 이러한 실행 결과는 후속 개발에서 확인한다.
